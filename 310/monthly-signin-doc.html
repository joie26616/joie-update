📖 需求说明

V1 现状签到为「周 7 天单套」(tab_SignInRecharges,无 VIP 维度、断签清零、无补签)。本期升级为「月 31 天 · 分 VIP 路线 · 里程碑奖励 · 补签」;后台采用单模版制(每 VIP 一套 31 天配置,按当月实际天数 28/29/30/31 自动截断),里程碑判定方式支持连续 / 累计,并新增领奖有效期。

玩法总览

  • 周期:按自然月。每月 1 号(或当月首次签到)选「当前 VIP 等级及以下」路线,当月锁定不可改;月底清零;下月 1 号重选。
  • 当月升级:升级不影响已锁定的本月路线,不可中途改;下月 1 号重选更高路线。
  • 基础签到:每个 VIP 等级自由配每日「充值门槛 + 奖励」;同一路线 1–31 天每天条件一致(可按天改)。建议值:vip1 充 100 送 2 / vip5 充 1000 送 30 / vip10 充 10000 送 500。
  • 里程碑奖励(满签阶梯):节点运营可自由增删(默认 3 / 7 / 15 天)+ 满签大奖恒落当月最后一天;判定方式可选「连续签到 / 当月累计签到」(仅影响节点判定;事实与判定分离,历史数据零回填)。详见「里程碑奖励」章节。
  • 补签:只能往前补 N 天(后台「补签天数」默认 5);需充值 = 当天充值金额 × 段倍率,补发比例默认 50%,无次数上限;确认补签跳存款页。
  • 领取:分两类 —— 每日签到奖(签到页弹框)/ 节点与满签大奖(达成即发放,按 🆕领奖有效期[当月末 23:59 / 达成后 N 天 / 不限,发放时快照]纳入 309 一键领取)。详见「领取模型」。
  • 后台配置 · 单模版制:每 VIP 仅 1 套 31 天配置、全月通用;批量工具(一键填充 / 区间修改 / 批量生成节点 / 跨 VIP 递增生成)仅为辅助,参数不落库。详见「后台配置」章节。
  • 数据统计:做进 V1「会员签到记录」(只加字段不改结构)—— 🆕判定方式 / 累计天数列、满签进度中性文案、统计小结含 签到奖励合计 / 总充值(= 查询范围内参与签到会员的充值总额)/ 签到奖励÷总充值 + 按判定方式分列。

⚙️ 后台配置(单模版制)

结构 = 每 VIP 一套 31 天配置:每日签到 + 连续签到奖励(独立配置)+ 补签分段;自然月按实际天数自动截断。

✅ 配置方案定稿:单模版制(每 VIP 仅 1 套 31 天,全月通用)。方案1(VIP×12 月)、方案2(VIP×3 模版)均已弃用(文件/口径留存备查);数据模型见《310-月签到-单模版配置数据模型(定稿).md》。

单模版制(每 VIP 一套 31 天 · 全月通用)

  • VIP × 1 套 31 天配置,所有月份共用(业务已确认同 VIP 各月一致)。
  • 自然月按实际天数 28/29/30/31 自动截断(平年 2 月 28 天同样覆盖);满签大奖恒落当月最后一天。
  • 录入量 12 → 1;跨 VIP 用「生成/复制到其他 VIP」弹窗(结构照源、按系数预填差异值)。
  • 连续签到奖励(节点)独立配置、可自由增删;补签需充值 = 当天充值金额 × 倍率(自动计算)。

🏅 里程碑奖励(满签阶梯)

阶梯进度 = 签到天数(含补签),判定口径由后台「奖励判定方式」决定 —— 连续签到(默认)或 当月累计签到;从「第 1 天」(当月首签 / 选线日)起算。节点默认 3 / 7 / 15 / 当月最后一天大奖,节点可由运营自由增删调。

节点说明

  • 节点(默认 3 / 7 / 15 天):运营可自由增删调;按所选判定方式的天数达标即可领该档阶梯奖。
  • 月末大奖:连续模式 = 连续签到至当月最后一天;累计模式 = 当月累计签满整月天数(2 月 28/29 天即得,30 天月 30 天即得)。
  • 连续中断(仅连续模式):某天漏签且超过 5 天补签期 → 连续中断,阶梯进度变为「当下实际连续天数」,断点及之后阶梯置「不可达」;累计模式无"中断"概念 —— 漏签仅不累加,已获进度不受影响。
  • 窗口内有漏签(可补)该节点仍「进行中」并提示「需补签 N 天达成」。

判定方式与历史数据保护(设计说明)

需求背景:里程碑奖励支持「连续签到」与「累计签到」两种判定方式后,需要保证历史数据不受配置变更影响,也不能污染现有数据模型。
设计原则 · 事实与判定分离:① 事实数据只记录客观签到结果,不因业务规则变化而改变;② 判定方式记录当月采用的奖励规则,并在创建会员月记录时固化,后续配置调整不影响历史数据。
  • 1. 签到事实独立记录:会员月记录同时维护两项签到数据 —— 连续签到天数 与 累计签到天数(包含补签);两项数据始终同步维护、互不覆盖,不因当前奖励模式不同而改变记录方式。
  • 2. 判定方式快照:会员月记录新增「判定方式」字段,创建当月签到记录时按当时的签到配置写入(连续签到 / 累计签到);之后即使运营修改模板,也不影响当月及历史月份的数据判定。历史数据该字段为空时默认按「连续签到」处理,保证兼容旧数据、无需数据回填。
  • 3. 展示规则:凡涉及里程碑奖励进度、已领奖励的页面,统一按会员月记录中的「判定方式」展示 —— 连续模式用连续签到天数计算、累计模式用累计签到天数计算;页面文案保持中性表述(如「已达成 X 天节点」),避免固定使用「连续签到 X 天」;如有需要,可增加「判定方式」筛选条件。
  • 4. 统计规则:所有里程碑奖励相关统计均按会员月记录中的「判定方式」计算;统计范围跨越不同月份、且各月判定方式不同时,分别按各自规则计算,确保统计结果准确。
设计收益:① 配置切换不会影响历史数据;② 无需修改已有签到事实数据结构,仅新增「判定方式」记录业务规则;③ 保持向下兼容,历史数据无需迁移;④ 为后续签到规则扩展提供稳定的数据基础。

↩️ 补签机制

漏签可补,只能往前补 N 天(后台「补签天数」配置·默认 5·0 = 关闭·无次数上限)。

分段倍数(按当月实际天数动态)

漏签日区间充值门槛倍数说明
1–5 天×2越早漏签成本越低
6–10 天×3
11–15 天×4
16–20 天×5
21–25 天×7
26–31 天×10小月不存在则该段不出现

补签规则

  • 补签条件 = 基础充值 × 区间倍数;确认补签 → 跳转存款页(recharge-page.html),先充值达倍数门槛。
  • 补签成功后该日打钩、计入连续;但补签的单日奖励只补发一半(30 → 15)。
  • 前台删除「剩余 N/N 次」次数额度显示,改按「补签天数」窗口展示可补范围。
  • 日历格区分两态:漏签·可补(可点补签)/ 漏签·超 5 天不可补(置灰)。

月中首签者

  • 首签 / 选线日 = 打卡卡片「第 1 天」,阶段从该日起算。
  • 当月日历仍展示之前日期:首签日前 5 天内 = 可补签;更早 = 置灰不可补。
  • 例:6/10 首签选线 → 6/5–6/9 显示可补,6/1–6/4 置灰不可补。
补签倍数高(26–31 天 ×10)+ 补发半额 → 补签率低,本意即抬高补签成本、以防刷为先;文案明示「补签需更高充值、奖励减半」。

🎁 领取模型(两类两条路)

每日签到奖与满签里程碑奖走不同领取路径。

A · 每日签到奖(当天即得)

  • 领取 / 反馈在签到页自身弹框完成(在现有弹框基础上优化)。
  • bonus collection 中沿用现状:作为「跳转参加(Check)」项,点击跳转签到页;不内联领取、不纳入一键领取。
  • 补签的单日奖(补发半额)同走此路,签到页弹框反馈。

B · 满签里程碑奖(3/7/15/月末)

  • 满足条件时,签到页提示「点击领取」(走优化后反馈弹框)。
  • bonus collection 新增「待领取」状态项,可在此领取。
  • 纳入「一键领取」,与其他活动奖聚合领取,体验统一。
复用 309 统一领取规范:领取成功弹窗(单项 / 多项 + 合计)+ 一键领取;沿用 V1 msgCode(已领 / 不满足 / 已过期 / 未到时间 / 勿重复提交);幂等去重。

🧩 扩展能力设计(未来可选,不影响当前版本)

背景:当前签到系统存在两个潜在业务扩展需求 —— ① 全年统一模板 + 特殊月份覆盖规则;② 仅允许指定月份开放签到。业务已确认:默认"每月规则一致",复杂覆盖属于未来可能出现的运营需求(如春节 / 周年活动),目前不需要落地。

该设计属于预留扩展能力,不构成当前版本开发范围。

一、设计原则

  • 当前版本不引入月份维度复杂逻辑;
  • 所有复杂能力遵循 YAGNI(You Aren't Gonna Need It,不预先实现);
  • 当前系统保持最小复杂度:扩展路径已论证,但不提前建设。

二、扩展方向 A · 月度配置覆盖能力(未来扩展 · 仅描述不实现)

  • 现状:系统无月份维度,每 VIP 一套 31 天配置全月通用,改模版即作用于所有月份;
  • 若未来需要"某些月份特殊规则"(春节 / 周年庆单独调奖励金额或充值条件),通过「配置覆盖层」实现:默认模版不动,按「VIP × 具体年月」存放稀疏覆盖(只存被改的字段,空 = 继承默认);
  • 不改动现有签到主流程 —— 签到 / 补签 / 发奖 / 前台展示的调用方零改动;
  • 覆盖合并只发生在统一读取入口 GetSignInConfig 内部(默认模版 ⊕ 月覆盖 merge);
  • 发奖沿用发放时快照机制(金额 / 领奖截止写死进会员记录),配置变更不污染历史数据。
结论:👉 当前不实现,仅预留扩展点(两个前置条件 —— 读取入口收口、发放快照 —— 已在本版落地)。

三、扩展方向 B · 月份级开放控制(未来扩展 · 仅描述不实现)

  • 现状:活动只有全局启用 / 停用开关,不支持"仅 3 月开放 / 仅 6、7、8 月开放";
  • 推荐方案(仅描述):新增 SignInOpenMonth(月维度控制表,记录开放的具体年月;无记录 = 长期开放);GetSignInConfig 入口增加一次开放校验(未开放月返回"未开放",前台隐藏入口);默认逻辑不变;
  • 口径约束:月签到以自然月为周期,开放粒度必须为整月;"春节期间"折算为所在整月开放,日粒度短周期玩法属于另一活动形态,不塞入本活动。
结论:👉 当前不实现,仅作为低成本扩展方案留档。

四、技术约束(硬性)

❗ 不允许新增复杂配置体系(通用配置中心 / 节日模板 / 国家模板等一律不做)。
❗ 不允许引入月份维度的核心模型重构(现有「模版 4 表 + 会员锁档表」结构不动)。
所有未来扩展必须同时满足:① 不影响现有签到流程(调用方零改动);② 不影响历史数据(发放快照隔离);③ 不影响现有 API。
✔ 唯一允许的扩展方式:「入口层扩展(GetSignInConfig 内部)+ 新增轻量表结构」 —— 覆盖表 / 开放月份表均为纯增量,可独立上线、独立回退。

五、输出目标(评审 / 开发一致口径)

  • 当前系统保持极简(单模版 + 唯一读取入口 + 发放快照);
  • 已考虑未来扩展路径(A 月度覆盖 / B 月份开放,方案与成本已论证);
  • 不提前实现任何复杂逻辑;
  • 技术改动成本最小化为明确设计原则:扩展 = 入口内部 merge / 校验 + 轻量新表;B 成本远低于 A,若都排期建议先 B 后 A。
再次声明:该设计属于预留扩展能力,不构成当前版本开发范围。
